17. CI/CD sử dụng GitHub Actions / GitHub Actions là gì?

Giới thiệu

GitHub Actions là nền tảng CI/CD và tự động hoá được tích hợp sẵn ngay trong GitHub. Thay vì phải dựng một server Jenkins riêng (như Section 10) hay cấu hình CodePipeline (Section 9), với GitHub Actions bạn chỉ cần viết một file YAML trong repository để build, test và deploy ứng dụng mỗi khi có sự kiện xảy ra: push code, tạo pull request, tạo tag, hay chạy thủ công. Toàn bộ pipeline chạy trên máy ảo do GitHub quản lý, không cần máy chủ riêng.

GitHub Actions – CI/CD được tích hợp ngay trong GitHub

Các khái niệm cơ bản

Để làm việc với GitHub Actions, bạn cần nắm 6 khái niệm sau — chúng là "từ vựng" xuất hiện trong mọi file workflow:

Khái niệmÝ nghĩaVí dụ
WorkflowQuy trình tự động hoá, định nghĩa trong một file .yml ở .github/workflows/. Một repository có thể có nhiều workflow.build-docker.yml, blue-green-deployment.yml
EventThứ kích hoạt workflow chạy.push, pull_request, workflow_dispatch (chạy tay), schedule
JobMột nhóm các bước chạy trên cùng một runner. Các job chạy song song theo mặc định, có thể ràng buộc thứ tự bằng needs.job build-and-push, job deploy
StepĐơn vị nhỏ nhất trong một job. Mỗi step là một Action hoặc một câu lệnh shell (run).step Checkout code, step docker build
ActionThành phần có thể tái sử dụng (giống thư viện/plugin), đóng gói sẵn một tác vụ.actions/checkout@v4, aws-actions/amazon-ecr-login@v2
RunnerMáy chạy job: ubuntu-latest, windows-latest, macos-latest hoặc máy tự quản lý (self-hosted).runs-on: ubuntu-latest

Cấu trúc file workflow

Một workflow tối giản trông như sau. Hãy đối chiếu từng phần với bảng khái niệm bên trên:

name: Build and Push Docker Image     # Tên workflow (hiển thị trên tab Actions)

on:                                   # Event kích hoạt workflow
  push:
    branches:
      - master
  workflow_dispatch: {}                # Cho phép chạy thủ công từ giao diện

jobs:                                 # Danh sách các job
  build-and-push:                     # Tên job
    runs-on: ubuntu-latest            # Runner chạy job
    steps:                            # Các step trong job
    - name: Checkout code
      uses: actions/checkout@v4       # Dùng action checkout

    - name: Build image
      run: docker build -t my-app .   # Chạy lệnh shell

Đặc điểm / tính năng chính

  • Tự động hoá toàn bộ quy trình: test, build và deploy đều có thể tự động hoá theo event của GitHub.
  • Tích hợp sâu với GitHub: dùng chính các event của repository (push, PR, tag, issue...) để kích hoạt action, không cần webhook cấu hình thủ công.
  • Hỗ trợ nhiều ngôn ngữ & hệ điều hành: runner có sẵn cho Linux, Windows, macOS; dễ dàng cài Node.js, Java, Python, Go...
  • Cộng đồng mạnh mẽ: hàng nghìn action chia sẻ công khai trên GitHub Marketplace, dùng lại được ngay (checkout, setup-node, các action của AWS...).
  • Hiệu quả về chi phí: GitHub cung cấp một lượng phút chạy miễn phí mỗi tháng cho repository public (và một phần cho private repo theo gói).
  • Reusable workflow & Environment: gọi workflow từ workflow khác (workflow_call) và kiểm soát release bằng environment kèm người duyệt (approval).

Pricing

Bảng giá GitHub Actions (có thể thay đổi theo thời gian)
  • Public repository: runner do GitHub cung cấp là miễn phí không giới hạn.
  • Private repository: có một lượng phút + dung lượng lưu trữ miễn phí mỗi tháng theo gói (Free/Team/Enterprise), dùng quá sẽ tính phí.
  • Chi phí thực tế phụ thuộc hệ điều hành runner (Linux rẻ nhất, macOS đắt hơn) và gói GitHub đang dùng. Kiểm tra trang Billing của tài khoản để biết số dư chính xác.

Trade-off

✅ Ưu điểm

  • Không cần dựng và bảo trì máy chủ CI riêng (so với Jenkins).
  • Tích hợp sẵn với GitHub, thiết lập nhanh bằng vài dòng YAML.
  • Kho action phong phú, đặc biệt có các action chính thức của AWS (aws-actions/*).
  • Cú pháp YAML dễ đọc, dễ review cùng code (pipeline as code).
  • Public repo chạy miễn phí; dễ dàng kích hoạt bằng push/PR/tag.

⚠️ Nhược điểm

  • Phụ thuộc vào GitHub — khó tái sử dụng nếu dùng GitLab/Bitbucket.
  • Private repo có giới hạn phút miễn phí; chạy nhiều sẽ tốn phí.
  • Debug local kém tiện hơn một số công cụ chạy được ngay trên máy.
  • Workflow phức tạp (nhiều điều kiện, tái sử dụng) có thể khó đọc nếu không tổ chức tốt.
  • Self-hosted runner cần tự lo bảo mật và bảo trì.
  • Nên dùng khi source code đã nằm trên GitHub và muốn một pipeline đơn giản, nhanh gọn, không muốn vận hành thêm hạ tầng CI.
  • Không nên dùng khi tổ chức chuẩn hoá trên một công cụ CI khác (Jenkins, GitLab CI...), hoặc cần kiểm soát tuyệt đối môi trường build (dùng self-hosted runner).

Use Cases

CI cho mọi pull request

Mỗi khi có PR, workflow tự chạy lint, unit test và build để bảo vệ chất lượng trước khi merge vào nhánh chính.

Build & push Docker image lên ECR

Push code (hoặc tạo tag) → GitHub Actions build image và đẩy lên Amazon ECR, sẵn sàng cho ECS kéo về chạy (nội dung Lab của chương này).

Deploy lên AWS

Dùng các action của AWS (configure-aws-credentials, amazon-ecr-login...) kết hợp AWS CLI để triển khai lên ECS, S3, Lambda...

Thông tin bổ sung

  • Bảo mật credential: Access Key không được commit vào repo. Lưu trong Settings → Secrets and variables → Actions của repository, rồi tham chiếu bằng ${{ secrets.TÊN }}.
  • Least privilege: IAM User dùng cho GitHub Actions chỉ nên có đúng quyền cần thiết (vd PowerUserAccess cho bài lab, thực tế nên viết policy hẹp hơn).
  • Giới hạn: mỗi workflow tối đa ~ 6 giờ; một job có tối đa 255 steps; số job chạy đồng thời phụ thuộc gói GitHub.
  • So với CodePipeline / Jenkins: Section 9 dùng dịch vụ AWS, Section 10 dùng Jenkins server tự quản — GitHub Actions là lựa chọn thứ ba, gắn liền với hệ sinh thái GitHub.
  • Tiết kiệm chi phí: hạn chế chạy job trên macOS/windows khi không cần, dùng workflow_dispatch cho tác vụ build thủ công thay vì kích hoạt liên tục.
