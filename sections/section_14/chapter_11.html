13. Kubernetes (k8s) cơ bản / Ingress: định tuyến HTTP/HTTPS

Giới thiệu

Ingress là một API object cung cấp quy tắc định tuyến HTTP/HTTPS từ bên ngoài cluster đến các Service bên trong. Thay vì tạo một LoadBalancer riêng cho từng Service, Ingress cho phép bạn định tuyến nhiều Service chỉ qua một entrypoint duy nhất dựa trên hostname và URL path. Ingress cần một Ingress Controller (nginx, traefik, istio...) để hoạt động.

Đặc điểm chính

  • Routing theo hostname: service-a.localhost và service-b.localhost trỏ tới 2 Service khác nhau.
  • Routing theo path: /service-a, /service-b trên cùng một host.
  • Một entrypoint: chỉ cần một IP công khai và một load balancer (đặt trước Ingress Controller) cho toàn bộ Service.
  • Hoạt động ở Layer 7: Ingress chỉ xử lý traffic HTTP/HTTPS; muốn expose TCP/UDP thuần (database, MQTT...) vẫn dùng Service NodePort/LoadBalancer.
  • Hỗ trợ TLS: có thể terminate HTTPS tại Ingress bằng certificate lưu trong Secret.
  • Cần Controller: Ingress chỉ là "khai báo rule"; Ingress Controller mới là thành phần thực thi các rule đó. Không có Controller thì Ingress không có tác dụng.

Mô hình kiến trúc

Ingress định tuyến theo hostname: foo.example.com → Service A, bar.example.com → Service B, mọi host khác (*) → Service C

Mỗi rule trong Ingress gồm host (tuỳ chọn), path và backend (tên Service + port). Request không khớp rule nào sẽ rơi vào rule không khai báo host (host=* trong hình) hoặc defaultBackend. Service vẫn làm nhiệm vụ gom nhóm các Pod (qua label selector) và trỏ tới targetPort 3000 của container.

Ingress Controller Pod đọc rule của Ingress object rồi điều hướng traffic tới Service/Pod tương ứng
Hiểu đúng luồng traffic: Ingress là object chứa rule (lưu trong API Server), không phải một "trạm" mà traffic đi xuyên qua. Mũi tên từ Ingress Controller Pod → my-app ingress nghĩa là Controller watch & đọc rule. Traffic thực tế đi như sau: Client → Service LoadBalancer/NodePort của Ingress Controller → Ingress Controller Pod (vd nginx) → Pod backend. Controller dùng Service để tra danh sách endpoint (IP các Pod) và thường gửi request thẳng tới Pod, không đi qua ClusterIP.

Các loại Ingress Controller phổ biến

  • Proxy chạy trong cluster (là Pod): Kubernetes Nginx Ingress Controller (ingress-nginx), Traefik, HAProxy, Kong, Istio.
  • Dùng load balancer của cloud: AWS Load Balancer Controller (tên cũ: AWS ALB Ingress Controller), GCP GLBC/GCE Ingress, AKS Application Gateway Ingress Controller. Với loại này, Controller chỉ cấu hình LB; traffic đi qua LB của cloud chứ không đi qua Pod Controller.
  • Một cluster có thể chạy nhiều Controller; Ingress chọn Controller qua trường spec.ingressClassName (vd nginx, alb).

AWS Load Balancer Controller trên AWS (tham khảo)

Trên EKS, AWS Load Balancer Controller (tên cũ alb-ingress-controller như trong hình) biến Ingress thành một Application Load Balancer:

Mô hình Ingress sử dụng ALB trên AWS (các bước 1 → 5)
  1. (1) Watch changes: Controller lắng nghe thay đổi Ingress từ API Server và cập nhật trạng thái (địa chỉ DNS của ALB) ngược lại vào Ingress.
  2. (2) ALB: một ALB được tạo trên AWS, dạng Internet-facing hoặc Internal. Mặc định mỗi Ingress tạo một ALB; có thể dùng IngressGroup (annotation alb.ingress.kubernetes.io/group.name) để nhiều Ingress dùng chung một ALB.
  3. (3) Target Group: mỗi Service backend tương ứng một Target Group, có 2 mode:
    • Instance mode: target là các Node (EC2) qua NodePort → Service phải là kiểu NodePort (hoặc LoadBalancer).
    • IP mode: target là IP của Pod, ALB gửi thẳng tới Pod, Service có thể là ClusterIP. Yêu cầu Pod có IP thật trong VPC — AWS VPC CNI trên EKS mặc định cấp secondary IP từ ENI cho mỗi Pod.
  4. (4) Listener: được tạo trên ALB, mỗi listener gắn với một port (vd 80 – HTTP, 443 – HTTPS).
  5. (5) Rule: mỗi host/path trong Ingress thành một listener rule trên ALB (vd /products → ServiceB, /accounts → ServiceC).

Yêu cầu trước khi bắt đầu

  • Hoàn thành Lab 1 (Minikube chạy), đã có Docker và tài khoản Docker Hub.

Các bước thực hành

  1. Bước 1: Build 2 Docker image

    Checkout repo mẫu (Node.js đơn giản):

    git clone https://github.com/hoanglinhdigital/nodejs-random-color
cd nodejs-random-color

    Sửa trang index để in message ServiceA, build và push image đầu tiên (thay <your-dockerhub-account>):

    docker build -t <your-dockerhub-account>/nodejs-random-color:service-a .
docker push <your-dockerhub-account>/nodejs-random-color:service-a

    Sửa lại trang index để in message ServiceB, build và push image thứ hai:

    docker build -t <your-dockerhub-account>/nodejs-random-color:service-b .
docker push <your-dockerhub-account>/nodejs-random-color:service-b

    💡 Kiểm tra trên Docker Hub có đủ 2 image đã push. Nếu không tự build, bạn có thể dùng image có sẵn của giảng viên hoanglinhdigital/nodejs-random-color:service-a|service-b.

  2. Bước 2: Tạo file cấu hình (Ingress theo host)

    Tạo file ingress-demo.yaml gồm 2 Deployment, 2 Service ClusterIP và 1 Ingress routing theo host:

    # service-a (Deployment + Service)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: service-a
spec:
  replicas: 2
  selector:
    matchLabels:
      app: service-a
  template:
    metadata:
      labels:
        app: service-a
    spec:
      containers:
      - name: service-a
        image: hoanglinhdigital/nodejs-random-color:service-a
        ports:
        - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: service-a
spec:
  type: ClusterIP
  selector:
    app: service-a
  ports:
  - protocol: TCP
    port: 3000
    targetPort: 3000
---
# (service-b tương tự, image ...:service-b)
# ...
---
# Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: "service-a.localhost"
    http:
      paths:
      - pathType: Prefix
        path: "/"
        backend:
          service:
            name: service-a
            port:
              number: 3000
  - host: "service-b.localhost"
    http:
      paths:
      - pathType: Prefix
        path: "/"
        backend:
          service:
            name: service-b
            port:
              number: 3000

    💡 File đầy đủ (cả service-b) nằm tại ingress/ingress-demo.yaml; biến thể định tuyến theo path nằm tại ingress-demo-path.yaml.

  3. Bước 3: Bật Ingress Controller

    Ingress chỉ hoạt động khi có Controller. Trên Minikube, bật addon ingress (cài ingress-nginx) và đợi Pod controller ở trạng thái Running:

    minikube addons enable ingress
kubectl get pods -n ingress-nginx
kubectl get ingressclass

    💡 kubectl get ingressclass hiển thị class nginx — chính là giá trị ingressClassName trong file YAML.

  4. Bước 4: Apply cấu hình và mở tunnel 
    kubectl apply -f ingress-demo.yaml
kubectl get all
kubectl get ingress

    Mở một terminal khác và chạy tunnel (giữ terminal này luôn chạy):

    minikube tunnel
  5. Bước 5: Truy cập qua sub-domain

    Mở trình duyệt tới http://service-a.localhost và http://service-b.localhost, hoặc dùng curl:

    curl http://service-a.localhost
curl http://service-b.localhost

    Bạn sẽ thấy lần lượt message ServiceA và ServiceB – tức Ingress đã định tuyến đúng theo hostname.

  6. Bước 6: Xoá resource 
    kubectl delete -f ingress-demo.yaml

Troubleshoot

Trình duyệt không mở được service-a.localhost
Nguyên nhân: chưa bật ingress addon hoặc chưa chạy minikube tunnel.
Giải pháp: chạy minikube addons enable ingress rồi minikube tunnel (giữ terminal).
Ingress trả 503 Service Temporarily Unavailable
Nguyên nhân: Ingress không tìm thấy backend (tên Service / port sai) hoặc Pod chưa Ready.
Giải pháp: kiểm tra kubectl get pods và tên Service/port trong rule Ingress khớp với Service.
Ingress trả 404 Not Found hoặc kubectl get ingress không có ADDRESS
Nguyên nhân: host trong request không khớp rule, hoặc ingressClassName không khớp Controller nào nên Ingress không được xử lý.
Giải pháp: kiểm tra kubectl describe ingress example-ingress, so sánh ingressClassName với kết quả kubectl get ingressclass.

Thông tin bổ sung

  • On Minikube: bật controller bằng minikube addons enable ingress, sau đó dùng minikube tunnel để truy cập.
  • Định tuyến theo path: có thể dùng annotation nginx.ingress.kubernetes.io/rewrite-target: / để "xoá" prefix path trước khi gửi cho Service.
  • TLS/HTTPS: Ingress có thể cấu hình TLS bằng certificate (Secret kiểu kubernetes.io/tls, khai báo trong spec.tls) để phục vụ HTTPS. Trên AWS, ALB dùng certificate từ ACM.
  • Gateway API: Ingress API đã ổn định nhưng không còn được bổ sung tính năng; Kubernetes khuyến nghị Gateway API (Gateway, HTTPRoute) cho dự án mới. Dự án ingress-nginx cũng đã được thông báo ngừng phát triển — khi triển khai thực tế hãy cân nhắc Controller khác hoặc Gateway API. Bài lab vẫn dùng addon ingress của Minikube vì đơn giản cho người mới.
  • Liên hệ Section 14: trên EKS, bạn sẽ dùng AWS Load Balancer Controller để tạo ALB cho Ingress.
