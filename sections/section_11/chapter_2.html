11. Chiến lược deployment cho Database / Lab: RDS Blue/Green Deployment kết hợp ECS Blue/Green

Mục tiêu

Tình huống thực tế: ứng dụng Expense Management (Next.js + Prisma) đang chạy production trên ECS Fargate với database RDS MySQL 8.0. MySQL 8.0 trên RDS đã hết standard support từ 31/07/2026, nên AWS tự động tính phí Extended Support. Nhiệm vụ của bạn là nâng cấp database lên MySQL 8.4 (LTS), sau đó release phiên bản ứng dụng mới, và cả hai việc đều phải gần như không có downtime.

  • Dựng toàn bộ hạ tầng của ứng dụng bằng Terraform: VPC 3 tầng, ALB, ECS Fargate, RDS MySQL, ECR, CodePipeline, CodeBuild, CodeDeploy.
  • Quản lý username/password database bằng AWS Secrets Manager: Terraform tự sinh password, ECS Task Definition đọc DATABASE_URL từ secret thay vì để giá trị thật trong biến môi trường.
  • Tạo RDS Blue/Green Deployment: Green chạy MySQL 8.4, dùng parameter group mới và instance class Graviton db.t4g.small.
  • Kiểm chứng Green được đồng bộ dữ liệu liên tục từ Blue và ở chế độ read-only.
  • Thực hiện switchover và đo thời gian gián đoạn bằng script gọi API liên tục. Ứng dụng không cần đổi endpoint.
  • Release ứng dụng v2 bằng ECS Blue/Green với CodeDeploy: kiểm thử qua test listener :8080, rồi Reroute traffic (có thể rollback).
  • Đồng bộ lại Terraform state sau khi thao tác trên Console, rồi dọn dẹp toàn bộ resource.

App (ECS) và database (RDS) có hai cơ chế Blue/Green độc lập. ECS dùng 2 Target Group và CodeDeploy để chuyển traffic. RDS dùng logical replication và switchover đổi tên instance, nên endpoint giữ nguyên, và secret chứa DATABASE_URL cũng không phải sửa.

Kịch bản release trong bài lab

Vì sao nâng cấp database trước, release app sau? Mỗi lần chỉ thay đổi một thành phần. Khi có lỗi, bạn biết ngay nguyên nhân nằm ở đâu. App v1 chạy được trên cả MySQL 8.0 và 8.4, nên nâng cấp database không bắt buộc phải sửa app. Nguyên tắc chung: các thay đổi database phải tương thích ngược (expand) và đi trước, app mới đi sau, còn việc dọn dẹp phần cũ (contract) làm cuối cùng.

Yêu cầu trước khi bắt đầu

  • Đã học chương Blue/Green cho database: Amazon RDS Blue/Green Deployments (chapter 1 của section này) và lab ECS Blue/Green với CodeDeploy ở Section 9.
  • Tài khoản AWS có quyền Administrator. Region dùng trong lab: ap-southeast-1 (Singapore).
  • Terraform >= 1.5, AWS CLI v2 đã cấu hình profile (aws sts get-caller-identity chạy được).
  • Tài khoản GitHub, Git, VS Code, Git Bash (Windows) để chạy script .sh.
  • MySQL Workbench để kết nối và kiểm tra database Blue và Green.
  • Source code lab: sourcecode/section_11_deployment_strategy/lab-rds-blue-green/.

Chi phí: bài lab dùng các resource tính phí theo giờ: NAT Gateway, ALB, ECS Fargate, RDS. Trong lúc Blue/Green tồn tại, bạn trả tiền cho 2 RDS instance. Instance MySQL 8.0 còn bị tính thêm phí RDS Extended Support (theo vCPU-giờ). Hãy làm liên tục trong một buổi (khoảng 3 giờ) và dọn dẹp ngay khi xong.

Các bước thực hành

Phần 1 – Chuẩn bị hạ tầng & deploy app v1

  1. Bước 1: Fork repository ứng dụng

    Truy cập github.com/hoanglinhdigital/lab-expense-management và Fork về tài khoản GitHub của bạn với các thông số:

    • Repository name: lab-expense-management
    • Copy the master branch only: bật

    Trong repo vừa fork, vào Settings → Actions → General và chọn Disable actions. Workflow deploy.yml có sẵn trong repo dành cho Vercel, không dùng trong lab này.

    Các file quan trọng của repo mà pipeline sẽ dùng:

    • Dockerfile + docker/entrypoint.sh: khi container khởi động sẽ tự chạy prisma migrate deploy + prisma db seed (tạo user mẫu demo@example.com / password123).
    • buildspec.yml: CodeBuild build image, push lên ECR, sinh taskdef.json và appspec.yaml.
    • appspec.yaml: CodeDeploy dùng file này để biết container nào cần gắn vào Target Group.
  2. Bước 2: Tạo connection tới GitHub

    Vào Developer Tools → Settings → Connections (region ap-southeast-1) và tạo connection với các thông số:

    • Provider: GitHub
    • Connection name: expense-mgmt-github
    • GitHub App: cài AWS Connector for GitHub vào tài khoản của bạn, cho phép truy cập repo lab-expense-management

    Đợi trạng thái connection là Available, sau đó copy ARN (dạng arn:aws:codeconnections:ap-southeast-1:<account-id>:connection/...).

  3. Bước 3: Lấy địa chỉ IP public của máy bạn

    IP này dùng để chỉ cho phép máy của bạn kết nối RDS (port 3306) và ALB test listener (port 8080).

    curl -s https://checkip.amazonaws.com
203.0.113.10

    Ghi lại IP theo dạng CIDR /32, ví dụ 203.0.113.10/32.

  4. Bước 4: Cấu hình Terraform

    Mở thư mục sourcecode/section_11_deployment_strategy/lab-rds-blue-green/terraform/environments/dev bằng terminal và tạo file terraform.tfvars từ file mẫu:

    cd sourcecode/section_11_deployment_strategy/lab-rds-blue-green/terraform/environments/dev
cp terraform.tfvars.example terraform.tfvars

    Mở terraform.tfvars bằng VS Code và điền các giá trị bắt buộc:

    BiếnGiá trị
    allowed_ip_cidrs, allowed_test_cidrsIP ở Bước 3, vd ["203.0.113.10/32"]
    alert_emailEmail của bạn
    github_ownerGitHub username của bạn
    codestar_connection_arnARN connection ở Bước 2

    Các giá trị quan trọng cho bài lab đã được đặt sẵn trong file mẫu:

    • db_engine_version = "8.0", db_instance_class = "db.t3.small", db_active_parameter_group = "mysql80": đây là môi trường Blue.
    • rds_public_access_enabled = true: chỉ dành cho lab, để MySQL Workbench trên máy bạn kết nối được tới Blue và Green.
    • deployment_ready_action_on_timeout = "STOP_DEPLOYMENT", deployment_ready_wait_minutes = 60: CodeDeploy dừng lại để bạn kiểm thử, rồi tự bấm Reroute traffic.
    Bạn không cần khai báo password database. Terraform tự sinh password 24 ký tự (resource random_password), dùng nó để tạo RDS, rồi lưu vào Secrets Manager cùng username (mặc định expense_admin). terraform.tfvars vẫn nằm trong .gitignore, không commit file này lên Git.
  5. Bước 5: Tạo hạ tầng bằng Terraform 
    terraform init
terraform plan
terraform apply -auto-approve

    Quá trình tạo mất khoảng 15–20 phút, chủ yếu là thời gian chờ RDS. Khi hoàn tất, xem output:

    terraform output

    Ghi lại alb_dns_name, alb_test_url, rds_identifier, rds_parameter_group_green, db_secret_name, codepipeline_name. Kiểm tra hộp thư và bấm Confirm subscription cho 2 email SNS (alert và CI/CD).

    Kiểm tra cách Terraform quản lý credential database:

    • Secrets Manager → Secrets → expense-mgmt/dev/rds-mysql-01 → Retrieve secret value: secret chứa các key username, password, host, port, dbname, DATABASE_URL.
    • ECS → Task definitions → expense-mgmt-dev-task-app-01 (revision mới nhất) → container → Environment variables: DATABASE_URL có kiểu ValueFrom, giá trị là ARN của secret kèm key (...:DATABASE_URL::), không hiển thị password.
    • IAM → Roles → expense-mgmt-dev-role-ecs-execution-01: inline policy chỉ cho phép secretsmanager:GetSecretValue trên đúng secret này. ECS agent dùng execution role để đọc secret và inject vào container lúc task khởi động.
    Ngay sau khi apply, tab Events của ECS Service có thể báo lỗi CannotPullContainerError cho image :latest. Đây là chuyện bình thường, vì ECR chưa có image nào. Image thật sẽ do pipeline build ở bước sau.
  6. Bước 6: Chờ pipeline deploy app v1 & Reroute traffic lần đầu

    Vào CodePipeline → pipeline expense-mgmt-dev-codepipeline-app-01. Pipeline tự chạy lần đầu ngay sau khi được tạo: Source → Build (khoảng 5–10 phút, build Next.js) → Deploy.

    Khi stage Deploy ở trạng thái In progress, bấm Details để mở deployment trên CodeDeploy. Đợi tới khi Step 1 (deploy replacement task set) và Step 2 (route test traffic) hoàn tất, rồi bấm Reroute traffic.

    Đợi deployment chuyển sang Succeeded rồi truy cập http://<alb_dns_name>. Đăng nhập bằng demo@example.com / password123, sau đó tạo vài khoản chi tiêu (menu Ghi chép) để database có dữ liệu.

Phần 2 – RDS Blue/Green: nâng cấp MySQL 8.0 → 8.4

  1. Bước 7: Kết nối MySQL Workbench tới database Blue

    Vào RDS → Databases → expense-mgmt-dev-rds-mysql-01, copy Endpoint trong tab Connectivity & security. Tạo connection trong MySQL Workbench:

    • Connection Name: BLUE - expense-db
    • Hostname: endpoint vừa copy, Port: 3306
    • Username / Password: giá trị username / password trong secret expense-mgmt/dev/rds-mysql-01 (Retrieve secret value ở Bước 5), chọn Store in Vault để nhập password

    Hoặc lấy username/password bằng AWS CLI:

    aws secretsmanager get-secret-value --secret-id expense-mgmt/dev/rds-mysql-01 --query SecretString --output text --region ap-southeast-1

    Mở file scripts/verify_queries.sql trong Workbench và chạy lần lượt câu 1, 2, 3. Ghi lại kết quả:

    SELECT @@version AS mysql_version, @@read_only AS read_only;   -- 8.0.x | 0
SHOW VARIABLES LIKE 'slow_query_log';                          -- OFF
  2. Bước 8: Tạo Blue/Green Deployment

    Trong RDS → Databases, chọn expense-mgmt-dev-rds-mysql-01, vào Actions → Create Blue/Green Deployment và nhập các thông số:

    • Blue/Green Deployment identifier: expense-db-upgrade-84
    • Engine version for green: MySQL 8.4.x (chọn bản 8.4 mới nhất)
    • DB parameter group for green: expense-mgmt-dev-pg-mysql84-01 (output rds_parameter_group_green)
    • DB instance class for green: db.t4g.small (Graviton, rẻ hơn db.t3.small)
    • Các thông số còn lại: giữ mặc định

    RDS sẽ chạy pre-check nâng cấp, tạo Green từ snapshot của Blue, nâng cấp Green lên 8.4, rồi thiết lập replication. Quá trình này mất khoảng 20–40 phút. Đợi Blue/Green deployment chuyển sang trạng thái Available.

    Trong danh sách Databases bạn sẽ thấy một nhóm gồm 3 dòng: Blue/Green deployment expense-db-upgrade-84, instance Source expense-mgmt-dev-rds-mysql-01, và instance Target expense-mgmt-dev-rds-mysql-01-green-xxxxxx.

    Green dùng cùng subnet group, Security Group và cấu hình public access với Blue, nên Workbench trên máy bạn kết nối được tới Green mà không phải cấu hình thêm.
  3. Bước 9: Kiểm tra database Green

    Copy endpoint của instance Green và tạo connection Workbench thứ hai tên GREEN - expense-db (cùng username/password trong secret, vì Green được tạo từ Blue nên giữ nguyên master user). Chạy câu 1, 2, 3, 5 trong verify_queries.sql:

    SELECT @@version AS mysql_version, @@read_only AS read_only;   -- 8.4.x | 1
SHOW VARIABLES LIKE 'slow_query_log';                          -- ON  (parameter group mysql84)
SELECT COUNT(*) FROM expense_db.`transaction`;                 -- bằng với BLUE
SHOW REPLICA STATUS;                                           -- Replica_IO_Running = Yes, Replica_SQL_Running = Yes

    So sánh với kết quả trên Blue ở Bước 7: Green đã ở version mới, dùng parameter group mới, nhưng dữ liệu vẫn giống hệt Blue.

  4. Bước 10: Kiểm chứng đồng bộ dữ liệu Blue → Green

    Trên app (http://<alb_dns_name>), tạo một khoản chi mới với ghi chú Test Blue/Green. App vẫn ghi vào Blue như bình thường.

    Trên connection GREEN, chạy câu 4:

    SELECT id, type, amount, note, createdAt
FROM expense_db.`transaction`
ORDER BY createdAt DESC
LIMIT 5;

    Chỉ sau vài giây, giao dịch Test Blue/Green đã xuất hiện trên Green. Bạn cũng có thể xem metric ReplicaLag của instance Green trong tab Monitoring.

  5. Bước 11: Kiểm chứng Green là read-only

    Trên connection GREEN, chạy câu 6:

    UPDATE expense_db.`user` SET name = 'test-write-green' WHERE email = 'demo@example.com';
-- Error Code: 1290. The MySQL server is running with the --read-only option so it cannot execute this statement

    Đây là cơ chế bảo vệ: nếu có ai ghi nhầm vào Green, dữ liệu Green sẽ lệch với Blue và replication có thể bị lỗi. Green chỉ dùng để đọc và kiểm thử (chạy query của app, đo hiệu năng, kiểm tra tương thích với 8.4).

  6. Bước 12: Chạy script đo downtime

    Tạo file check_downtime.sh trên máy (hoặc dùng file trong scripts/), copy nội dung từ sourcecode/section_11_deployment_strategy/lab-rds-blue-green/scripts/check_downtime.sh. Mỗi giây, script gọi API POST /api/auth/login. Request này vừa đọc bảng user vừa ghi vào bảng session, nên phản ánh đúng trạng thái đọc/ghi của database.

    Mở một cửa sổ Git Bash riêng và chạy (thay bằng alb_dns_name của bạn):

    bash check_downtime.sh expense-mgmt-dev-alb-01-123456789.ap-southeast-1.elb.amazonaws.com
10:15:01  HTTP 200  OK
10:15:02  HTTP 200  OK
10:15:03  HTTP 200  OK

    Giữ script chạy trong suốt Bước 13.

  7. Bước 13: Switchover

    Trong RDS → Databases, chọn Blue/Green deployment expense-db-upgrade-84, vào Actions → Switch over với các thông số:

    • Switchover timeout: 300 giây (mặc định)

    Trước khi switch, RDS kiểm tra các guardrail: replication lag, transaction đang chạy lâu, trạng thái hai môi trường... Trong lúc switchover, RDS chặn ghi trên Blue, đợi Green bắt kịp, rồi đổi tên instance:

    • Green → expense-mgmt-dev-rds-mysql-01 (nhận endpoint cũ, trở thành production)
    • Blue cũ → expense-mgmt-dev-rds-mysql-01-old1

    Quan sát cửa sổ script: thường chỉ có vài dòng FAIL (HTTP 500 hoặc 000) trong khoảng dưới 1 phút. Sau đó app tự kết nối lại tới endpoint cũ, lúc này đã trỏ sang instance MySQL 8.4. Nhấn Ctrl + C để xem tổng số request OK/FAIL.

    Nếu switchover vượt timeout hoặc guardrail không đạt, RDS huỷ switchover và Blue tiếp tục chạy như cũ. Đây là điểm khác biệt quan trọng so với nâng cấp trực tiếp (modify instance).
  8. Bước 14: Kiểm tra sau switchover

    Trong RDS Console, mở expense-mgmt-dev-rds-mysql-01 và xác nhận: Engine version 8.4.x, Class db.t4g.small, tab Configuration hiển thị parameter group expense-mgmt-dev-pg-mysql84-01.

    Trên connection BLUE của Workbench (endpoint cũ, không sửa gì), bấm Reconnect rồi chạy lại câu 1, 2, 7:

    SELECT @@version AS mysql_version, @@read_only AS read_only;   -- 8.4.x | 0  (đã ghi được)
SHOW VARIABLES LIKE 'slow_query_log';                          -- ON
SELECT user, host, plugin FROM mysql.user WHERE user NOT LIKE 'rds%' AND user NOT LIKE 'mysql.%';
-- user tạo từ 8.0 vẫn dùng mysql_native_password -> app không phải đổi gì

    Trên app, tạo thêm một khoản chi mới để xác nhận ghi dữ liệu bình thường. Nhờ endpoint không đổi, ECS task không cần restart, và secret DATABASE_URL trong Secrets Manager không phải sửa (host vẫn là endpoint cũ, password vẫn giữ nguyên).

Phần 3 – ECS Blue/Green: release app v2 với CodeDeploy

  1. Bước 15: Thay đổi code app v2 và push

    Trên repo fork của bạn (VS Code sau khi clone, hoặc sửa trực tiếp trên GitHub), mở file src/app/components/AuthBrandHeader.tsx và đổi dòng:

    <p className="text-sm text-white/85">Quản lý chi tiêu thông minh</p>

    thành:

    <p className="text-sm text-white/85">Quản lý chi tiêu thông minh – v2 (MySQL 8.4)</p>

    Commit và push lên nhánh master:

    git add src/app/components/AuthBrandHeader.tsx
git commit -m "release v2: update brand header"
git push origin master
  2. Bước 16: Theo dõi pipeline và CodeDeploy

    CodePipeline tự trigger khi có commit mới. Sau khi Build xong, mở deployment của stage Deploy trên CodeDeploy và quan sát các bước:

    • Step 1: Deploying replacement task set: ECS tạo task set mới (v2) và đăng ký vào Target Group tg-app-02.
    • Step 2: Test traffic route setup: listener :8080 trỏ tới task set v2.
    • Step 3: Rerouting production traffic: CodeDeploy dừng ở đây, chờ bạn bấm Reroute traffic (tối đa 60 phút).

    Task v2 khi khởi động sẽ tự chạy prisma migrate deploy trên database MySQL 8.4. Vì không có migration mới nên bước này kết thúc ngay.

  3. Bước 17: Kiểm thử v2 qua test listener

    Mở 2 tab trình duyệt (chế độ ẩn danh để tránh cache) và so sánh:

    • http://<alb_dns_name>/login (production :80): dòng chữ "Quản lý chi tiêu thông minh", tức v1.
    • http://<alb_dns_name>:8080/login (test, output alb_test_url): dòng chữ "... – v2 (MySQL 8.4)", tức v2.

    Đăng nhập vào v2 trên :8080, xem lại các khoản chi đã tạo. Cả v1 và v2 đều dùng chung một database. Bật lại script đo downtime ở cửa sổ Git Bash:

    bash check_downtime.sh expense-mgmt-dev-alb-01-123456789.ap-southeast-1.elb.amazonaws.com
  4. Bước 18: Reroute traffic

    Trên trang deployment của CodeDeploy, bấm Reroute traffic. Listener :80 chuyển sang tg-app-02 (v2). Script đo downtime sẽ không có dòng FAIL nào, vì cả 2 task set đều healthy trong lúc ALB đổi Target Group.

    Refresh http://<alb_dns_name>/login: lúc này đã là v2. CodeDeploy chuyển sang Step 4: Wait 5 minutes trước khi terminate task set v1.

  5. Bước 19 (tuỳ chọn): Rollback

    Trong 5 phút chờ ở Step 4, bấm Stop and roll back deployment → chọn Reroute traffic to original task set. Listener :80 quay về v1 ngay lập tức, vì task set v1 vẫn đang chạy.

    Để release lại v2, vào CodePipeline bấm Release change, rồi lặp lại Bước 16 → 18 và đợi deployment Succeeded.

    Hãy so sánh: rollback app (ECS) chỉ là đổi Target Group, mất vài giây. Còn với RDS, sau switchover không có nút switch back: instance -old1 không nhận dữ liệu mới. Vì vậy phải kiểm thử Green thật kỹ trước khi switchover.

Phần 4 – Hoàn tất RDS Blue/Green & đồng bộ Terraform

  1. Bước 20: Xoá Blue/Green deployment và instance cũ

    Sau khi app chạy ổn định trên MySQL 8.4, dọn môi trường cũ trong RDS → Databases:

    • Blue/Green deployment expense-db-upgrade-84: Delete. Sau switchover, thao tác này chỉ xoá đối tượng Blue/Green, không xoá instance nào.
    • Instance expense-mgmt-dev-rds-mysql-01-old1: Delete, bỏ chọn Create final snapshot và Retain automated backups.

    Instance -old1 vẫn chạy MySQL 8.0 nên vẫn bị tính phí instance và phí Extended Support cho tới khi bạn xoá nó.

  2. Bước 21: Đồng bộ Terraform state với thực tế

    Terraform AWS provider v5 theo dõi aws_db_instance bằng Resource ID (db-XXXX), không phải bằng tên. Sau switchover, Resource ID trong state là của instance -old1 (đã xoá), trong khi instance production hiện tại là Green cũ. Phải cho Terraform "nhận" lại instance mới:

    terraform state rm module.database.aws_db_instance.this
terraform import module.database.aws_db_instance.this expense-mgmt-dev-rds-mysql-01

    Sửa 3 dòng trong terraform.tfvars cho khớp với Green:

    db_engine_version         = "8.4"
db_instance_class         = "db.t4g.small"
db_active_parameter_group = "mysql84"

    Kiểm tra plan:

    terraform plan

    Plan không được có dòng must be replaced hay destroy nào cho aws_db_instance. Chỉ có thể có update in-place cho password, skip_final_snapshot, apply_immediately, vì các thuộc tính này không được đọc về khi import. Password ở đây là giá trị của random_password trong state, giống hệt password đang dùng, nên apply không làm thay đổi credential. Secret cũng không đổi vì host không đổi. Nếu plan đúng như vậy thì apply:

    terraform apply -auto-approve
    Không chạy terraform apply sau switchover trước khi làm bước này. State cũ đang trỏ vào instance -old1, nên Terraform sẽ cố đổi tên/sửa instance cũ để khớp với code. Bài học rút ra: mọi thay đổi làm trên Console đối với resource do Terraform quản lý đều phải được đồng bộ ngược vào code và state.

Troubleshoot

Pipeline lỗi ở stage Source: Could not access the CodeConnections connection
Nguyên nhân: Connection còn ở trạng thái Pending, GitHub App chưa được cấp quyền truy cập repo fork, hoặc ARN trong terraform.tfvars sai.
Giải pháp: Vào Developer Tools → Connections, chọn Update pending connection, cấp quyền repo lab-expense-management, rồi Release change lại pipeline.
CodeBuild lỗi toomanyrequests: You have reached your pull rate limit
Nguyên nhân: Dockerfile kéo image node:20-alpine từ Docker Hub và bị giới hạn số lần pull ẩn danh.
Giải pháp: Trong repo fork, đổi cả 3 dòng FROM node:20-alpine thành FROM public.ecr.aws/docker/library/node:20-alpine rồi push lại.
Không tạo được Blue/Green deployment: lỗi về binary logging / backup
Nguyên nhân: RDS MySQL cần automated backup (backup_retention_period > 0) để bật binlog phục vụ replication.
Giải pháp: Giữ backup_retention_period = 7 như trong module database. Nếu đã sửa thành 0, đặt lại rồi terraform apply.
Blue/Green deployment báo Invalid configuration / pre-check nâng cấp thất bại
Nguyên nhân: Pre-check nâng cấp 8.0 → 8.4 phát hiện vấn đề không tương thích (từ khoá bị loại bỏ, cấu hình không còn hỗ trợ...).
Giải pháp: Vào instance Blue → tab Logs & events, mở file PrePatchCompatibility.log để xem chi tiết, xử lý rồi xoá và tạo lại Blue/Green deployment.
Terraform không tạo được RDS MySQL 8.0 (version không còn hỗ trợ)
Nguyên nhân: Theo thời gian, AWS có thể ngừng cho tạo mới instance với version cũ.
Giải pháp: Tạo Blue với db_engine_version = "8.4" và db_active_parameter_group = "mysql84". Ở Bước 8, giữ engine version, chọn parameter group default.mysql8.4 cho Green và đổi instance class sang db.t4g.small. Quy trình Blue/Green vẫn giống hệt.
ECS task dừng với ResourceInitializationError: unable to pull secrets or registry auth
Nguyên nhân: Execution role không có quyền secretsmanager:GetSecretValue trên secret, ARN/key trong valueFrom sai, hoặc task không ra được Internet để gọi Secrets Manager.
Giải pháp: Kiểm tra inline policy policy-ecs-execution-secret-01 của role role-ecs-execution-01, kiểm tra secret có key DATABASE_URL, và kiểm tra route NAT Gateway của App subnet.
terraform apply lỗi a secret with this name is already scheduled for deletion
Nguyên nhân: Bạn đã destroy với lab_force_destroy = false, nên secret cũ vẫn trong thời gian chờ xoá 7 ngày.
Giải pháp: Xoá hẳn secret cũ rồi apply lại:
aws secretsmanager delete-secret --secret-id expense-mgmt/dev/rds-mysql-01 --force-delete-without-recovery --region ap-southeast-1
MySQL Workbench không kết nối được (timeout)
Nguyên nhân: IP public của bạn đã thay đổi so với allowed_ip_cidrs, hoặc rds_public_access_enabled = false.
Giải pháp: Chạy lại curl -s https://checkip.amazonaws.com, cập nhật allowed_ip_cidrs và allowed_test_cidrs, rồi terraform apply. Nếu đang trong giai đoạn Blue/Green, chỉ chạy apply sau khi kiểm tra plan không đụng tới aws_db_instance.
http://<alb_dns_name>:8080 bị timeout
Nguyên nhân: Security Group của ALB chỉ mở port 8080 cho allowed_test_cidrs, hoặc CodeDeploy chưa tới Step 2.
Giải pháp: Kiểm tra IP trong allowed_test_cidrs và đợi Step 2 hoàn tất.
Switchover bị huỷ: Switchover timed out / guardrail không đạt
Nguyên nhân: Replication lag lớn, có transaction chạy lâu trên Blue, hoặc Green chưa ở trạng thái Available.
Giải pháp: Blue không bị ảnh hưởng. Đợi ReplicaLag của Green về 0, đóng các query chạy lâu trong Workbench, rồi switch over lại.
Sau switchover, app trả HTTP 500 kéo dài hơn vài phút
Nguyên nhân: Connection pool của app giữ các kết nối đã bị ngắt và không tự kết nối lại được.
Giải pháp: Xem log trong CloudWatch Log group /ecs/expense-mgmt-dev-app-01. Để làm mới kết nối, vào ECS Service và stop task đang chạy, service sẽ tự tạo task mới. Trong thực tế, app cần có cơ chế retry/reconnect như đã học ở chương lý thuyết.
terraform plan sau import vẫn đòi must be replaced instance RDS
Nguyên nhân: Giá trị trong terraform.tfvars không khớp thực tế, ví dụ sai db_name hoặc db_username, hay quên đổi db_active_parameter_group.
Giải pháp: Không apply. Đọc dòng có ghi chú # forces replacement trong plan, sửa terraform.tfvars cho khớp với instance trên Console, rồi plan lại.

Dọn dẹp resource

NAT Gateway, ALB, ECS Fargate và RDS đều tính phí theo giờ, kể cả khi không có traffic. Instance RDS MySQL 8.0 còn bị tính thêm phí Extended Support. Hãy dọn dẹp ngay sau khi hoàn thành lab.
  1. Nếu chưa làm Bước 20: xoá Blue/Green deployment expense-db-upgrade-84 và instance -old1. Nếu chưa switchover, khi xoá Blue/Green deployment hãy chọn xoá cả Green.
  2. Nếu chưa làm Bước 21: chạy terraform state rm + terraform import như ở Bước 21. Nếu không, terraform destroy sẽ không xoá được instance RDS production hiện tại, và DB subnet group sẽ bị kẹt.
  3. Xoá toàn bộ hạ tầng bằng Terraform. ECR repository và S3 bucket artifact được xoá luôn dù còn image/object, nhờ lab_force_destroy = true:
terraform destroy -auto-approve
  1. Vào RDS → Databases và RDS → Snapshots / Automated backups, kiểm tra không còn instance hay backup nào của expense-mgmt-dev.
  2. Vào Secrets Manager, kiểm tra secret expense-mgmt/dev/rds-mysql-01 đã bị xoá. Với lab_force_destroy = true, recovery window = 0 nên secret bị xoá ngay.
  3. Vào Developer Tools → Settings → Connections, xoá connection expense-mgmt-github nếu không dùng nữa.
  4. (Tuỳ chọn) Xoá repo fork lab-expense-management trên GitHub và connection Workbench BLUE/GREEN.

Thông tin bổ sung

  • Terraform cũng làm được Blue/Green: aws_db_instance có block blue_green_update { enabled = true }. Khi bạn đổi engine_version hoặc instance_class, Terraform tự tạo Blue/Green, switchover, rồi xoá instance cũ. Cách này tiện, nhưng bạn không có khoảng thời gian để kiểm thử Green như trong lab.
  • Schema change: nếu app v2 cần thay đổi schema, hãy viết migration theo kiểu expand (thêm cột cho phép NULL, thêm bảng, thêm index) để app v1 vẫn chạy được. Chỉ xoá/đổi tên cột (contract) ở lần release sau, khi không còn task v1 nào.
  • Migration chạy khi container khởi động (RUN_DB_SEED=true) chỉ phù hợp với dev và desired_count = 1. Ở production, nên tách migration thành một bước riêng trong pipeline để nhiều task không cùng chạy migrate một lúc.
  • Tiết kiệm chi phí: chỉ giữ Green trong lúc kiểm thử, và xoá -old1 ngay khi đã chắc chắn không cần rollback. Chuyển sang Graviton (db.t4g) thường rẻ hơn khoảng 10% so với db.t3 cùng kích thước.
  • Secrets Manager & Terraform state: password không còn nằm trong terraform.tfvars hay Task Definition, nhưng vẫn được lưu trong terraform.tfstate (giá trị của random_password và secret_string). Ở môi trường thật, hãy lưu state trên S3 backend có bật encryption và giới hạn quyền truy cập.
  • Vì sao không dùng manage_master_user_password? RDS có thể tự tạo và tự rotate secret cho master user, nhưng secret đó chỉ có username/password, trong khi app cần cả chuỗi DATABASE_URL. Ngoài ra ECS chỉ đọc secret lúc task khởi động: sau mỗi lần rotate, các task đang chạy vẫn giữ password cũ cho tới khi được deploy lại. Muốn dùng rotation, app phải tự ghép URL từ các key riêng lẻ, và phải có quy trình deploy lại sau khi rotate.
  • Chi phí Secrets Manager: khoảng 0.40 USD/secret/tháng (tính theo thời gian tồn tại) cộng 0.05 USD/10.000 API call. Trong một buổi lab, chi phí gần như bằng 0.
  • Bảo mật: rds_public_access_enabled chỉ dùng cho lab. Ở production, kết nối database qua bastion/SSM Session Manager hoặc CloudShell VPC environment, và bật TLS (database_ssl_enabled = true kèm RDS CA bundle).
