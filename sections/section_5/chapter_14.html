5. Infra as Code sử dụng Terraform / Lab 10: Triển khai Multi-environment, Multi-region

Mục tiêu

  • Triển khai cùng một hệ thống lên 2 môi trường dev (Singapore – ap-southeast-1) và test (Tokyo – ap-northeast-1).
  • Chỉ sử dụng một bộ modules chung, không duplicate code hạ tầng; mỗi môi trường chỉ khác nhau ở file biến.
  • Mỗi môi trường có state riêng trên S3 để thao tác môi trường này không ảnh hưởng môi trường kia.

Sơ đồ đề bài (slide gốc): mỗi môi trường có thể dùng state bucket riêng; trong lab này ta dùng chung 1 bucket với 2 key khác nhau cho đơn giản.

Yêu cầu trước khi bắt đầu

  • Hoàn thành Lab 9: đã có S3 bucket lưu state (ở Singapore) và đã destroy hạ tầng của Lab 9.
  • Code các module networking, security, compute từ Lab 6.
  • Keypair tại ~/terraform-labs/keypair/.
Chi phí: Lab tạo đồng thời 2 VPC, mỗi VPC có 1 NAT Gateway và 2 Elastic IP (NAT + EC2) — chi phí gấp đôi Lab 6. Destroy cả 2 môi trường ngay sau khi xong.

  2. Bước 2: Cấu hình môi trường dev (Singapore)

    Tạo dev-singapore/main.tf. Khác với Lab 9 ở 2 điểm: source = "../modules/..." và backend key = "dev/terraform.tfstate". Nhớ đổi tên bucket thành bucket của bạn:

    📄 lab10_multi_env/dev-singapore/main.tf

    terraform {
  required_version = ">= 1.10.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
  # Mỗi môi trường dùng một key (file state) riêng trong cùng một bucket
  backend "s3" {
    bucket       = "udemy-terraform-state-change-me"
    key          = "dev/terraform.tfstate"
    region       = "ap-southeast-1"
    encrypt      = true
    use_lockfile = true # S3 native state locking (Terraform >= 1.10), không cần DynamoDB
  }
}

provider "aws" {
  region = var.region
}

  3. Bước 3: Cấu hình môi trường test (Tokyo)

    test-tokyo/main.tf giống hệt dev, chỉ khác backend key = "test/terraform.tfstate". Backend vẫn ở region ap-southeast-1 vì bucket nằm ở Singapore, còn resource được deploy sang Tokyo theo var.region của provider:

  4. Bước 4: Deploy môi trường dev 
    cd ~/terraform-labs/lab10_multi_env/dev-singapore
terraform init
terraform apply -auto-approve
  5. Bước 5: Deploy môi trường test 
    cd ~/terraform-labs/lab10_multi_env/test-tokyo
terraform init
terraform apply -auto-approve

    Data source aws_ami tự tìm đúng AMI Amazon Linux 2023 của region Tokyo — đây là lý do ta không hard-code AMI ID ngay từ Lab 2.

  6. Bước 6: Kiểm tra 2 môi trường
    • Trên Console, chuyển region sang Singapore: VPC udemy-dev-vpc (10.0.0.0/16) và EC2 Udemy Demo.
    • Chuyển region sang Tokyo: VPC udemy-test-vpc (10.1.0.0/16) và EC2 Udemy Demo.
    • Trên S3 bucket: có 2 file state dev/terraform.tfstate và test/terraform.tfstate.

    SSH vào EC2 của môi trường test (đang đứng ở thư mục test-tokyo):

    ssh -i ../../keypair/udemy-key ec2-user@$(terraform output -raw instance_public_ip)
  7. Bước 7: Thay đổi một môi trường không ảnh hưởng môi trường kia

    Trong test-tokyo/terraform.tfvars đổi instance_type = "t3.small", chạy plan ở thư mục test:

    terraform plan
Plan: 0 to add, 1 to change, 0 to destroy.

    Plan chỉ thay đổi EC2 của Tokyo. Chuyển sang thư mục dev-singapore chạy terraform plan sẽ thấy No changes — hai môi trường hoàn toàn độc lập vì có state riêng.

    Mở rộng: Khi cần sửa hạ tầng cho mọi môi trường (ví dụ thêm 1 rule vào Security Group), bạn chỉ sửa một lần trong modules/, rồi lần lượt apply ở từng môi trường: dev → test → prod. Đây chính là quy trình promote thay đổi qua các môi trường.

Kiểm tra kết quả

✅ Lab thành công khi

  • Hai VPC và hai EC2 chạy ở 2 region Singapore và Tokyo, được tạo từ cùng một bộ module.
  • S3 bucket có 2 file state tách biệt cho dev và test.
  • Thay đổi biến ở môi trường test không làm plan của môi trường dev thay đổi.

Trade-off: các cách tổ chức multi-environment

Cách tổ chứcƯu điểmNhược điểm
Thư mục riêng cho từng môi trường (lab này)Rõ ràng, state tách biệt, mỗi môi trường có thể có backend/provider riêngLặp lại một ít code ở root module (main.tf, variable.tf)
Terraform workspace (terraform workspace new test)Dùng chung một thư mục code, đổi môi trường bằng một lệnhDễ nhầm workspace khi apply; các môi trường bắt buộc dùng chung backend
Công cụ bổ trợ (Terragrunt)Loại bỏ hoàn toàn code lặp, quản lý backend tự độngThêm một công cụ phải học và bảo trì

Troubleshoot

Unreadable module directory / no file exists at "../../keypair/udemy-key.pub"
Nguyên nhân: Sai đường dẫn tương đối tới modules hoặc keypair.
Giải pháp: Từ thư mục môi trường, kiểm tra ls ../modules và ls ../../keypair.
Apply ở test-tokyo nhưng plan muốn xoá resource của dev
Nguyên nhân: Hai môi trường dùng chung key trong backend → dùng chung state.
Giải pháp: Dừng lại, không apply. Sửa key của test thành test/terraform.tfstate, chạy terraform init -reconfigure.
InvalidParameterValue với availability zone ở Tokyo
Nguyên nhân: AZ ap-northeast-1b không khả dụng cho tài khoản.
Giải pháp: Dùng ap-northeast-1a, ap-northeast-1c hoặc ap-northeast-1d.

Dọn dẹp resource

Hai NAT Gateway và các Elastic IP ở 2 region đều tính phí theo giờ. Destroy cả 2 môi trường, sau đó chuyển region trên Console để kiểm tra lại cả Singapore và Tokyo.
cd ~/terraform-labs/lab10_multi_env/test-tokyo
terraform destroy -auto-approve
cd ~/terraform-labs/lab10_multi_env/dev-singapore
terraform destroy -auto-approve

Cuối cùng, xoá S3 bucket chứa state trên Console: chọn bucket → Empty (xoá toàn bộ object, bao gồm mọi version) → Delete.
