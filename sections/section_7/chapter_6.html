7. Thao tác cơ bản với Git / Các mô hình Git Workflow & chiến lược quản lý branch

Giới thiệu

Git Workflow (branching strategy) là bộ quy ước của team về cách tạo, đặt tên, merge branch và branch nào được deploy lên môi trường nào. Git không bắt buộc workflow nào cả, nhưng nếu không có quy ước chung, team sẽ gặp conflict liên tục, không biết code nào đang chạy trên production và CI/CD rất khó thiết kế. Chương này giới thiệu 3 mô hình phổ biến: Centralized, Feature Branch và Gitflow.

Đặc điểm chính

  • Centralized workflow: chỉ có 1 branch main, mọi người commit thẳng vào đó. Đơn giản nhưng dễ conflict.
  • Feature Branch workflow: mỗi tính năng/bug một branch riêng tạo từ branch chính, merge lại qua Pull Request.
  • Gitflow workflow: chia branch theo vai trò (main, develop, feature/*, bugfix/*, release/*, hotfix/*), phù hợp dự án lớn có lịch release rõ ràng.
  • Pull Request là “cổng kiểm soát”: code chỉ vào branch chính sau khi được review và CI chạy pass.
  • Branch được bảo vệ (protected branch): chặn push trực tiếp, chặn xoá, chặn force push vào main/develop.
  • Mapping branch ↔ môi trường: mỗi branch quan trọng tương ứng với một môi trường deploy (Dev, Test, Staging, Production) – nền tảng để thiết kế CI/CD.

  • Môi trường Dev: thường được deploy tự động ngay khi có Pull Request được merge vào develop (CI/CD).
  • Môi trường Test: dùng cho Integration Testing, release theo phiên bản từ nhánh release/*.
  • Môi trường Staging: dùng cho System Testing & UAT trước khi release cho end-user. Về cơ bản Staging phải giống Production.
  • Hotfix: nên test trên Staging trước khi merge vào main và deploy lên Production.
Lưu ý: các quy tắc mapping trên mang tính tham khảo, hoàn toàn có thể tuỳ biến theo quy mô dự án và yêu cầu khách hàng. Tuy nhiên, phá vỡ flow deployment chuẩn, apply hotfix quá nhiều, release không kèm testing sẽ khiến chất lượng dự án đi xuống và tốn nhiều effort để sửa chữa.

Nên dùng Gitflow khi dự án lớn, codebase phức tạp, có thời gian phát triển dài, có các đợt release rõ ràng và nhiều môi trường kiểm thử. Không nên dùng Gitflow cho team nhỏ deploy liên tục nhiều lần mỗi ngày – khi đó Feature Branch/GitHub Flow hoặc Trunk-based development (branch ngắn ngày, merge vào main hằng ngày, kết hợp feature flag) gọn hơn.

Use Cases

Dự án outsource cho khách hàng doanh nghiệp

Release theo sprint 2–4 tuần, khách hàng cần UAT trên Staging trước khi lên Production → Gitflow với release/* và tag version để dễ đối chiếu, rollback.

Startup SaaS deploy nhiều lần mỗi ngày

Team nhỏ, CI/CD tự động hoàn toàn → Feature Branch (GitHub Flow): mỗi PR merge vào main là deploy, giảm chi phí quản lý branch.

Repository Terraform/hạ tầng

Mỗi thay đổi hạ tầng là một feature branch, PR hiển thị kết quả terraform plan để review, merge thì CI/CD chạy terraform apply.

Thông tin bổ sung

  • Các lab tiếp theo áp dụng Gitflow: Lab 4 (protect branch + feature + PR), Lab 5 (release + tag), Lab 7 (conflict giữa 2 feature branch).
  • Quy ước đặt tên branch nên thống nhất từ đầu dự án: chữ thường, dùng / phân loại và gắn mã ticket, ví dụ feature/JIRA-123-login, bugfix/JIRA-456.
  • Xoá feature branch sau khi merge để danh sách branch gọn gàng (GitHub có tuỳ chọn tự động xoá head branch sau khi merge PR).
