17. CICD for Kubernetes/EKS / Giới thiệu GitOps

Giới thiệu

GitOps là phương pháp quản trị hệ thống và triển khai phần mềm mà trong đó Git đóng vai trò "nguồn sự thật duy nhất" (Single Source of Truth). Nói cách khác, mọi trạng thái mong muốn của hệ thống (hạ tầng, cấu hình, ứng dụng) đều được khai báo trong Git; một công cụ tự động sẽ làm cho hệ thống thực tế "khớp" với Git.

Cách thức hoạt động

GitOps dựa trên mô hình khai báo (Declarative): bạn không ra lệnh "hãy tạo cho tôi 3 máy chủ", mà viết file cấu hình định nghĩa "hệ thống này có 3 máy chủ". Quy trình diễn ra như sau:

3 bước của GitOps: khai báo trạng thái mong muốn trong Git → agent liên tục so sánh → tự điều chỉnh hệ thống thực tế cho khớp.

  • Khai báo cấu hình: mọi thiết lập hạ tầng (Infrastructure as Code) và ứng dụng đều được lưu trong Git.
  • So sánh trạng thái: một Agent (thường là ArgoCD hoặc Flux) liên tục so sánh trạng thái trên Git với trạng thái thực tế đang chạy.
  • Tự động đồng bộ (Reconciliation): nếu có sự khác biệt (vd bạn sửa số máy chủ từ 3 lên 5 trên Git), agent sẽ tự điều chỉnh hệ thống thực tế cho khớp với Git.

Tại sao GitOps mang lại lợi thế?

  • Tính minh bạch & lịch sử: ai sửa gì, sửa khi nào, tại sao sửa — tất cả nằm trong lịch sử commit của Git.
  • Khôi phục thảm hoạ siêu tốc: nếu hệ thống bị lỗi, chỉ cần rollback trên Git về phiên bản ổn định trước đó; hệ thống tự đưa mình về trạng thái cũ trong tích tắc.
  • Tính nhất quán: loại bỏ tình trạng "trên máy tôi chạy được mà trên server thì không" hoặc cấu hình thủ công gây sai sót giữa Dev/Staging/Prod.
  • Bảo mật: kỹ sư không cần quyền truy cập trực tiếp vào cluster; họ chỉ cần quyền đẩy code lên Git.

Các thành phần chính trong hệ sinh thái GitOps

  • Version Control: GitHub, GitLab...
  • Nền tảng điều phối: Kubernetes, EKS, ECS...
  • Công cụ CICD (GitOps agent): ArgoCD, FluxCD...
  • Quản lý cấu hình: Helm, Kustomize, Terraform...

GitOps khác gì với CI/CD truyền thống?

CI/CD truyền thống đẩy (push) thay đổi vào server; GitOps thì agent chủ động kéo (pull) trạng thái từ Git về để đồng bộ.

  • Push-based: công cụ CI (như Jenkins) "push" thay đổi vào server. Nếu server bị lỗi kết nối lúc đó, việc triển khai có thể thất bại nửa chừng.
  • Pull-based: server tự "pull" cấu hình về. Nếu có thay đổi ngoài ý muốn trên server (ai đó lỡ xoá một cấu hình), agent phát hiện sai lệch và tự sửa lại cho đúng với Git (tự phục hồi - self-healing).

Trade-off

✅ Ưu điểm

  • Audit & rollback dễ dàng nhờ Git (revert commit là xong).
  • Tự phát hiện và sửa drift (sai lệch) trên cluster.
  • Bảo mật tốt: không cần cấp quyền cluster trực tiếp cho developer.
  • Nhất quán, tái lập được môi trường dễ dàng.

⚠️ Nhược điểm

  • Phải cài và vận hành thêm agent (ArgoCD/Flux) trên cluster.
  • Khái niệm mới, cần thời gian làm quen với team.
  • Phải tách rõ "code ứng dụng" và "manifest" (thường là 2 repo khác nhau).

Use Cases

Hệ thống cần rollback nhanh

Khi phát hành lỗi, chỉ cần revert commit trong manifest repo để ArgoCD tự đưa cluster về bản ổn định.

Nhiều môi trường (dev/staging/prod)

Dùng manifest riêng theo môi trường trong Git, agent tự đồng bộ từng môi trường, đảm bảo nhất quán.

Quản trị tập trung, phân quyền chặt

Developer chỉ push code; chỉ một nhóm nhỏ có quyền duyệt thay đổi manifest, không ai cần truy cập cluster trực tiếp.
