17. CICD for Kubernetes/EKS / Các phương án implement CICD cho Kubernetes/EKS

Giới thiệu

Không có một "công thức duy nhất" để làm CI/CD cho EKS. Tuỳ vào yêu cầu dự án và kỹ năng của DevOps engineer, bạn có thể chọn một trong nhiều phương án. Các công cụ phổ biến trong hệ sinh thái gồm: Jenkins, GitHub Actions, GitLab CI, AWS CodePipeline (nhóm CI) và Helm, ArgoCD, Terraform (nhóm CD/quản lý cấu hình).

CI/CD có thể kết hợp linh hoạt: một công cụ CI (Jenkins/GitHub Actions/CodePipeline) với một cơ chế CD (kubectl/Helm/ArgoCD/Terraform).

Tiêu chí chọn phương án

  • Nơi đặt code: code trên GitHub thì GitHub Actions tiện; trên GitLab thì GitLab CI; cần managed AWS thì CodePipeline.
  • Kỹ năng đội ngũ: team đã quen Jenkins thì tiếp tục Jenkins + Helm; muốn đơn giản thì dùng GitHub Actions.
  • Nhu cầu vận hành: không muốn "nuôi" server CI thì chọn managed/SaaS (CodePipeline, GitHub Actions, GitLab CI SaaS).
  • Mức độ audit & rollback: cần truy vết "ai deploy gì, khi nào" và rollback dễ → ưu tiên GitOps (ArgoCD).
  • Chi phí: Jenkins self-hosted tốn EC2; CodePipeline/GitHub Actions tính phí theo phút build (có free tier).

Trade-off

✅ Managed / SaaS (CodePipeline, GitHub Actions)

  • Không lo cài đặt, bảo trì, nâng cấp.
  • Bảo mật tích hợp sẵn (IAM, secret, OIDC).
  • Triển khai nhanh, ít rào cản.

⚠️ Self-hosted (Jenkins) / GitOps (ArgoCD)

  • Jenkins: tự vận hành, phải lo HA, backup, bảo mật server.
  • ArgoCD: thêm một thành phần trên cluster cần quản lý, nhưng bù lại rollback & audit mạnh.

Use Cases

Doanh nghiệp truyền thống đã dùng Jenkins

Tiếp tục Jenkins + Helm để tận dụng kinh nghiệm sẵn có, ít tốn công chuyển đổi.

Startup code trên GitHub

Dùng GitHub Actions vì nằm ngay trên repo, miễn phí cho public repo và dễ duy trì.

Hệ thống cần audit chặt & rollback nhanh

Dùng GitOps với ArgoCD: mọi thay đổi đều qua Git, rollback chỉ là revert commit.

Thông tin bổ sung

Lộ trình của chương này: bạn sẽ thực hành 2 cách phổ biến là CodePipeline (Lab 2) và GitHub Actions (Lab 3), sau đó nâng cấp lên GitOps với ArgoCD (Lab 4) — từ đó tự rút ra ưu/nhược của từng cách.

Về bản chất, các công cụ chỉ là "phương tiện": luồng build image → push registry → deploy lên cluster là giống nhau. Nắm vững luồng này, bạn có thể chuyển đổi giữa các công cụ dễ dàng.
