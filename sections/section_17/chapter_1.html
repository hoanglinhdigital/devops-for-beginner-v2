17. CICD for Kubernetes/EKS / Tổng quan flow CI-CD cho Kubernetes/EKS

Giới thiệu

Ở các chương trước bạn đã học cách tạo EKS cluster và deploy ứng dụng thủ công bằng kubectl/helm. Nhưng trong một dự án thật, code thay đổi hàng ngày — việc build và deploy bằng tay vừa chậm vừa dễ sai. CI/CD cho Kubernetes/EKS là cách tự động hoá toàn bộ chuỗi: từ lúc developer push code cho tới lúc ứng dụng mới chạy trên cluster.

Điểm khác biệt lớn nhất so với deploy lên EC2 truyền thống: với Kubernetes, "sản phẩm" bạn deploy không phải là file war/jar hay thư mục, mà là Docker image được đóng gói rồi đẩy lên registry (ECR), sau đó Kubernetes cập nhật manifest (YAML) để chạy image đó.

Luồng CI/CD cho K8s: code đẩy lên Git → CI build Docker image → push lên ECR → CD cập nhật manifest và deploy lên EKS.

Các giai đoạn chính

  • Source (Quản lý mã nguồn): code nằm trong CodeCommit/GitHub/GitLab. Khi có commit/push, pipeline được kích hoạt (webhook/trigger).
  • Build (CI - Tích hợp liên tục): chạy test, build Docker image cho từng service (frontend, backend...), gắn tag cho image rồi đẩy lên registry (ECR).
  • Registry: nơi lưu trữ Docker image — thường là Amazon ECR. Kubernetes sẽ pull image từ đây khi deploy.
  • Deploy (CD - Triển khai liên tục): cập nhật image tag trong manifest YAML, rồi kubectl apply (hoặc helm upgrade) để Kubernetes triển khai phiên bản mới.
  • Verify: kiểm tra pod/deployment đã chạy, truy cập ứng dụng qua Load Balancer/Ingress để xác nhận bản mới hoạt động.

Nguyên tắc quan trọng khi CI/CD cho Kubernetes

  • Image là bất biến (immutable): không sửa vào container đang chạy, mà build image mới và deploy lại.
  • Manifest phải được version: manifest YAML nên nằm trong Git (kèm code hoặc tách repo riêng), giúp rollback dễ dàng.
  • Tag image rõ ràng: không nên chỉ dùng tag latest — dùng commit hash hoặc version để biết chính xác bản nào đang chạy.
  • Phân quyền tối thiểu: pipeline chỉ nên có quyền vừa đủ để push ECR và deploy lên namespace cần thiết.

Trade-off

✅ Ưu điểm

  • Tự động hoá hoàn toàn: push code là xong, không cần thao tác tay.
  • Nhất quán giữa môi trường (image giống nhau ở dev/staging/prod).
  • Rollback nhanh nhờ image tag và manifest lưu trong Git.
  • Tận dụng sức mạnh của K8s (rolling update, tự phục hồi, scale).

⚠️ Nhược điểm

  • Độ phức tạp cao hơn: cần hiểu Docker, K8s, manifest, registry.
  • Nhiều thành phần cần cấu hình và bảo mật (credential, IAM, secret).
  • Khó debug hơn khi lỗi nằm ở nhiều tầng (build, image, manifest, cluster).

Use Cases

Ứng dụng microservices trên EKS

Mỗi service là một image riêng, CI/CD tự build và deploy từng service khi code của nó thay đổi.

Monorepo frontend + backend

Một repo chứa cả FE/BE, pipeline phát hiện thư mục nào thay đổi để chỉ build đúng service cần thiết (tiết kiệm thời gian).

Release nhiều môi trường

Cùng một image deploy lên dev → staging → production bằng cách thay đổi manifest/config theo môi trường.
