8. Thao tác cơ bản với Docker / Container là gì? Tại sao cần Container?

Mục tiêu của section

  • Nắm được các khái niệm cơ bản về Container và Docker.
  • Cài đặt môi trường làm việc với Docker trên máy local (Windows/MacOS) hoặc EC2 Linux.
  • Biết cách thao tác với Image, Container, Dockerfile.
  • Thực hành Docker & Docker Compose qua các bài lab, từ 1 container đơn giản tới nhiều container có load balancer.
  • Làm quen với Amazon ECR & Amazon ECS – nền tảng cho các chương CI/CD và Kubernetes phía sau.

Giới thiệu

Container là một cách đóng gói ứng dụng cùng với mọi thứ cần thiết để chạy ứng dụng đó (runtime, thư viện, công cụ hệ thống, cấu hình) thành một đơn vị độc lập, có thể chạy giống hệt nhau ở bất cứ đâu có hỗ trợ container: laptop của developer, server test hay môi trường Cloud. Container ra đời để giải quyết các vấn đề kinh điển khi triển khai ứng dụng trực tiếp lên server/máy ảo (VM): xung đột thư viện, môi trường không nhất quán và triển khai chậm.

Câu chuyện: một ngày cài phần mềm lên server production

Hãy cùng xét mô hình triển khai truyền thống, nhiều ứng dụng chạy chung trên một VM/EC2 server:

  1. Sếp giao nhiệm vụ cài một software mới lên server production. Bạn tìm hiểu rất kỹ các thư viện, runtime cần thiết và tải về đầy đủ.

  2. Đến ngày thực hiện, việc đầu tiên là backup server (đương nhiên rồi 😄).

  3. Software mới cần thư viện Jxxx 20, nhưng trình cài đặt báo không thể tồn tại 2 version song song. Bạn gỡ Jxxx 19 ra và cài Jxxx 20 vào (mới hơn tất nhiên là tốt hơn?).

  4. Cài đặt xong, bạn báo sếp là đã hoàn thành.

  5. 30 phút sau, khách hàng gọi điện: một số software trước giờ vẫn chạy bình thường thì hôm nay không khởi động được và văng lỗi thiếu thư viện... 😱

Nhiều ứng dụng dùng chung một bộ thư viện trên cùng OS: nâng version cho App C làm App A, App B bị lỗi.

Các vấn đề khi triển khai trực tiếp trên VM

  • Xung đột version giữa library, binary, runtime khi cài nhiều ứng dụng trên cùng một VM.
  • Không độc lập môi trường giữa các ứng dụng: một ứng dụng thay đổi có thể ảnh hưởng ứng dụng khác.
  • Triển khai mất thời gian: chuẩn bị OS, cài thư viện, setup môi trường... lặp lại cho mỗi server.
  • Khó đảm bảo tính nhất quán: ứng dụng chạy OK trên máy dev nhưng không chắc chạy được trên server test/production (“It works on my machine!”).

Container giải quyết vấn đề như thế nào?

  • Đóng gói ứng dụng cùng những thứ cần thiết để chạy ứng dụng đó thành một image, có thể chạy ở bất cứ đâu có hỗ trợ container.
  • Cung cấp môi trường & cơ chế cấp phát tài nguyên (CPU, RAM, network, file system riêng) để image đó chạy cô lập với các ứng dụng khác.
  • Cung cấp công cụ cho phép đóng gói, lưu trữ, phân phối và triển khai ứng dụng một cách thuận tiện (build → push lên registry → pull → run).

Mỗi VM có một Guest OS đầy đủ (vài GB). Các container dùng chung kernel của Host OS, mỗi container chỉ chứa ứng dụng và thư viện của riêng nó (vài MB tới vài trăm MB).

Trên thực tế, container và VM không loại trừ nhau: trên AWS, container thường chạy bên trong EC2 (VM) hoặc Fargate (micro-VM do AWS quản lý).

Lợi ích của việc sử dụng Container

  • Độc lập với môi trường: đóng gói ứng dụng và toàn bộ dependencies (thư viện, tools...), giúp ứng dụng chạy độc lập và nhất quán trên mọi môi trường: Dev, Test, Staging, Production.
  • Đơn giản hoá quy trình triển khai: nhất quán, nhanh, thuận tiện; dễ dàng tích hợp vào pipeline CI/CD (build image 1 lần, deploy nhiều nơi).
  • Quản lý tài nguyên hiệu quả: chạy nhiều container trên cùng một máy chủ vật lý hoặc máy ảo, tận dụng tối đa CPU/RAM của hệ thống.
  • Linh hoạt & dễ mở rộng: scale horizontal bằng cách chạy thêm container để đáp ứng workload; chạy song song nhiều version của một ứng dụng.
  • Rollback nhanh: mỗi version là một image có tag, quay về version cũ chỉ cần chạy lại image cũ.
  • Phù hợp kiến trúc Microservices: mỗi service đóng gói thành container riêng, dùng ngôn ngữ/thư viện riêng mà không ảnh hưởng nhau.

Trade-off

✅ Nên dùng Container khi

  • Ứng dụng web/API, microservices cần deploy thường xuyên.
  • Cần môi trường Dev/Test/Prod nhất quán.
  • Cần scale nhanh theo traffic.
  • Muốn chuẩn hoá quy trình CI/CD cho nhiều ngôn ngữ khác nhau.

⚠️ Cân nhắc khi

  • Ứng dụng cần cô lập bảo mật tuyệt đối hoặc chạy OS/kernel khác (dùng VM).
  • Ứng dụng legacy phụ thuộc chặt vào phần cứng, GUI hoặc license theo máy.
  • Database production: container chạy được, nhưng nên ưu tiên dịch vụ managed (RDS, ElastiCache).
  • Team chưa có kiến thức container: cần thời gian học Docker, registry, orchestration.

Use Cases

Môi trường dev đồng nhất

Thành viên mới vào dự án chỉ cần cài Docker và chạy docker compose up là có đủ web, cache, database giống hệt các thành viên khác.

CI/CD build once – run anywhere

Pipeline build image 1 lần, đẩy lên registry (ECR), sau đó deploy cùng một image lên Dev → Staging → Production.

Microservices trên AWS

Mỗi service (user, order, payment) chạy trong container riêng trên ECS/EKS, scale độc lập theo tải của từng service.

Thông tin bổ sung

Container không phải công nghệ mới: Linux đã có các cơ chế chroot, namespaces (cô lập process, network, file system) và cgroups (giới hạn CPU/RAM) từ lâu. Docker (2013) giúp container trở nên phổ biến nhờ đóng gói các cơ chế này thành công cụ dễ dùng cùng định dạng image chuẩn hoá.
Tiêu chuẩn OCI: định dạng image và runtime container được chuẩn hoá bởi Open Container Initiative (OCI). Image build bằng Docker có thể chạy trên containerd, Podman, ECS, Kubernetes...
